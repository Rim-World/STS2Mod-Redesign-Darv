## 2. 根因

两个目标方法已被其他 mod 补丁：

| 目标 | 已有补丁 |
|---|---|
| `NRelicCollectionEntry._Ready` | MintySpire2 `OnRelicCollectionEntryReady`（Harmony Postfix） |
| `NRelicCollectionCategory.LoadRelics` | RitsuLib `RelicCollectionActListPatch`（Transpiler） |

叠加我们的 Postfix 后，MonoMod/Harmony 生成的组合方法 JIT 失败，抛 `ArgumentException: Value does not fall within the expected range`。异常发生在补丁体执行前，因此 `try/catch` 也抓不到；只有 Harmony Finalizer 能兜住。

这不是 `DarvSettings.Current` 的泛型读取问题：1.0.2 已把它改为启动期静态缓存，异常数量不变。

## 4. 兼容性判断

- **没有全局“目标所有权”规范**。Harmony 允许所有 mod 对同一方法叠加 Prefix/Postfix/Transpiler；`HarmonyPriority` / `HarmonyBefore` / `HarmonyAfter` 只决定顺序，不能阻止组合方法 JIT 失败。
- 可行的工程约定：
  - 优先公开 API/事件；没有 API 时选最少人碰的私有 helper。
  - 优先 Postfix，避免 Transpiler。
  - 目标用 `OptionalMethod`，补丁 `IsCritical=false`。
  - 加 `Finalizer`，保证外观补丁不拖垮原流程。
  - 只读公开成员；不直接碰 private 字段。
  - 用 `HarmonyPatchDump` / `Harmony.GetPatchInfo`（BaseLib 有 dump 工具）检查目标占用。
- 1.0.3 的 `LoadRelicNodes` 当前无已知占用，冲突面比 1.0.1/1.0.2 小；但仍不是“零冲突”保证。若未来其他 mod 也补丁 `LoadRelicNodes`，同样的 JIT 风险会回来，Finalizer 只能保证不拖垮图鉴。
