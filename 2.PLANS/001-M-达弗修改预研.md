# 001-M 达弗修改预研（资料汇总）

> 状态：预研草稿 v0.2（2026-08-23）。本文件只汇总**已确认的技术事实**与**候选技术路线**，不包含任何最终决定。
> 前置资料：`../3.DOCS/005-T-达弗现状机制与双版本差异.md`（达弗现状）、`../3.DOCS/001-R-BaseLib-StS2能力调研.md`、`../3.DOCS/002-R-STS2-RitsuLib能力调研.md`、`../3.DOCS/003-T-塔1遗物对照表.md`（塔1遗物对照，含 77 件塔1独有清单与 18 件移植候选）。

## 0. 需求描述（用户原话要点）

1. 修改达弗（Darv）的所有选项的概率分布与内容；
2. 可能引入一些《杀戮尖塔1》的遗物；
3. 同时适用于 default 107 与最新 beta 111 两个版本；
4. 不重复造轮子，尽可能依靠现成基础库与 API（baselib / ritsulib）；
5. 内容尚未决定（选项内容、概率目标、是否引入塔1遗物、引入哪些——均为开放问题）。

## 1. 已确认的技术事实（证据链见各调研文档）

| 事实 | 结论 |
|---|---|
| 达弗选项生成位置 | `Darv.GenerateInitialOptions()`（protected virtual，两版方法体逐字节相同）＋静态 `_validRelicSets`（107 为 9 集合、111 为 11 集合，仅此差异） |
| 概率机制 | 无权重概念：逐集合均匀抽 1 候选 → 洗牌 → NextBool 50% 取 2+DustyTome / 50% 取 3 |
| 池结构与过滤 | 无过滤 7 遗物（两版同）；Ectoplasm/Sozu 与 PhilosophersStone/VelvetChoker 的集合构成与 Act 过滤条件 107→111 有变化（详见现状报告 §3） |
| 出现机制 | 第 1 幕不出现；`RunManager.GenerateRooms` 对第 2、3 幕做**不放回**分配（池=[Darv] 时第 2 幕 50% 分到、未分到则第 3 幕再 50%），分到后与本幕 3 个 Ancient 均匀竞争 → 第 2 幕出现 12.5%、第 3 幕 6.25%、一局至少一次 18.75%；DarvEpoch 未解锁则不出现 |
| 选项数量约束 | 恒为 3 个（2+1 或 3）；`GenerateInitialOptionsWrapper`（sealed）只做收尾（Hook 放行、ReplaceNullOptions、DebugOption） |
| 双版本 patch 点 | `Darv.cs` 的实例方法/字段在两个版本签名一致（static ctor 内容不同）；自写 patch 无需版本分支（除非要保留各版本原池做基线） |
| 塔1遗物引入的技术路径 | 注册新 RelicModel（两库均支持）＋把它加入达弗候选（需 patch） |
| 本地化 | 达弗 50 键两版完全一致；达弗相关遗物文本唯一差异为 SOZU（语序/着色）；新增/改选项文本需自备本地化（游戏原生 res://{modId}/localization/{lang}/*.json 或两库的注入 API） |
| 塔1遗物背景 | 达弗 12 候选中有 11 件为塔1 BOSS 遗物直接移植（塔2 归入 Ancient 稀有度）；塔1 独有遗物精筛 77 件，其中 18 件为移植候选（详见塔1对照报告） |

## 2. 候选技术路线（三选一或组合）

### 路线 A：纯 Harmony patch（不依赖两个基础库）
- 做法：`[ModInitializer]` + `new Harmony(modId)`；Prefix 拦截 `Darv.GenerateInitialOptions` 整体替换生成逻辑（自定义池/权重/幕条件/选项数），同步替换 `AllPossibleOptions`。
- 优点：完全可控；不引入运行时依赖（玩家不用装 baselib/ritsulib）；沿用用户现有 5 个 mod 的成熟模式（Godot .NET 工程 + build.ps1 + 守卫懒评估）。
- 缺点：达弗的 `_validRelicSets`/`RelicOption` 等 private/protected 成员访问需 `Krafs.Publicizer`（用户 csproj 模板已支持，见 Setup.md 排查节）或反射；游戏更新后若方法签名变化需跟进（用户已有 mod 的守卫模式可降级为原版行为）。
- 新遗物注册：纯 patch 路线仍需自行完成遗物注册（仿照游戏 ModelDb 机制或参考现有 mod），工作量大些。

### 路线 B：依赖 ritsulib（追加选项用 `AncientOption<Darv>`，改池/概率自写 patch）
- 做法：`RegisterAncientOption<Darv>` 追加新选项（含塔1遗物）；用 ritsulib 的 `CreatePatcher` 脚手架写改池/概率的 patch；`RegisterRelic` 注册塔1遗物。
- 优点：塔1遗物注册、本地化、配置、持久化、调试面板开箱即用；工作坊 0.5.14 已带 0.107.1/0.111.0 兼容变体（用户环境零门槛）。
- 缺点：运行时依赖 ritsulib（manifest 声明依赖）；`AncientOption` 只增不减（若要"改原池"仍需 patch）；ritsulib 自身更新节奏快，0.111 支持依赖工作坊版跟进。

### 路线 C：依赖 baselib（`CustomAncientModel` 新建 Ancient，或纯做遗物注册/配置）
- 做法：用 `CustomRelicModel`/`CustomRelicPoolModel` 注册塔1遗物（进 `EventRelicPool`）；配置/本地化/存档用 BaseLib API；修改达弗本体仍自写 Harmony（BaseLib 无覆盖 vanilla 的 API）。
- 优点：官方模板（ModTemplate-StS2）标准依赖；遗物注册与配置 API 成熟；用户工作坊已装（v3.4.5）。
- 缺点：**不提供修改既有 Ancient 的任何 API**（已核实）；min_game_version 声明 0.107.1（0.107.0 未确认）；对 111 的兼容靠其 `BetaMainCompatibility` 反射适配。

### 组合建议（待用户定夺）
- 若追求"最小依赖"：路线 A（用户最熟悉）。
- 若追求"现成 API 最大化"：路线 B 为主（追加选项+注册遗物用 ritsulib，改池/概率用其 patch 脚手架），必要时叠加 C 的遗物注册能力。
- 两库可共存（ritsulib 有 BaseLib 桥接，不冲突）。

## 3. 内容与概率设计（开放问题，待用户决策）

1. **修改目标**：仅"概率分布"（保持 12 遗物，调权重）？还是同时"内容"（增删遗物）？还是两者都要？
2. **是否引入塔1遗物**：引入哪些？（候选清单见塔1遗物对照报告）引入后替换哪些原选项还是新增？数量？
3. **权重模型**：保持"均匀"改为自定义权重（如某遗物更稀有/更常见）？是否按幕/角色/牌组构成差异化？
4. **DustyTome 的 50% 掺入**：保留？调整概率？移除？
5. **双版本策略**：107 与 111 用同一套自定义池（统一覆盖）？还是各自保留原池基线、mod 只在其上做增量调整？（111 的池已与 107 不同，若 mod 覆盖则两版表现一致；若增量则需分别处理）
6. **选项数量**：保持 3 选 1？还是可配置 2/4/5 选？
7. **出现频率**：是否也修改达弗在 Act 的出现概率（原版第 2 幕 12.5%、第 3 幕 6.25%，需 patch RunManager/ActModel 的分配逻辑）？（用户原话聚焦"选项"，此项默认不动）
8. **塔1遗物移植的机制适配**：塔1遗物效果在塔2 引擎中如何实现（命令系统不同），哪些适合纯被动、哪些需要专门实现（见塔1遗物对照报告的适配性标注）。

## 4. 版本兼容与部署（已确认的环境事实）

- 用户环境：游戏 v0.111.0（release_info.json: v0.111.0, commit 41cef1ea）；Steam 可切 default 107。
- mod 部署：`mods/<ModId>/` 目录（dll + pck + json manifest）；用户已有 5 个 mod 已发布工作坊。
- manifest 关键字段：`min_game_version`（"0.107.0"）、`dependencies`（对象形式 `{"id": ..., "min_version": ...}`，0.105+ 支持）、`affects_gameplay: true`。
- 工作坊已装：BaseLib v3.4.5（lib/ 含 0.107.1/0.109.0/0.110.0/0.111.0 变体）、RitsuLib v0.5.14（lib/ 含 0.107.1/0.109.0/0.110.0/0.111.0 变体）——**两库在 107 与 111 下均有对应运行时变体**。
- 构建链：dotnet build（引用游戏目录 sts2.dll + 0Harmony.dll）→ Godot 导出 pck → 拷贝 mods/（用户 build.ps1 模式）或模板 Publish。
- 版本差异风险点：`Darv.cs` 两版差异仅在 static ctor；`EventModel/Rng/EventOption` 等基类 111 有重构（uint→ulong、序列化等），若 patch 触及基类需核对。
